# 变更说明

先查阅本次范围内的实际差异、相关决定和已有记录，确定改变了什么、为何改变、影响谁。资料中的提交顺序不自动成为成稿顺序。版本范围和事实依据清楚后，按读者用途组织内容。

## Release说明

面向使用者解释这一版值得了解的变化及其影响。优先介绍重要变化，再安排必要细节和获取方式。首次发布介绍本版提供什么及如何开始使用；后续发布围绕相对前一版本的变化展开。

将改动与使用者可感知的内容或行为联系起来；适用时说明调整前后的差别。没有依据时不声称速度、准确性或体验提高。内部重构、构建过程和执行检查只有在影响读者使用时才进入主要介绍。

需要使用者采取行动的变化具体写明，包括相关条件和步骤；影响使用的真实问题在相应位置交代。不要只贴提交标题，也不要把次要改动和主要变化排成没有主次的长清单。

## Changelog

按版本保留便于追踪的变化记录，遵循仓库既有格式。分类以读者查找方便为准，不为填满模板制造空栏目。内容应能说明具体变化、涉及范围和相关影响，不用“若干优化”“完善细节”等概括代替信息。

Release与Changelog可以互相链接，按各自用途控制解释程度，不要求两份文档逐字重复。

## Commit message

根据实际提交的差异概括这次变更，遵循仓库已有语言、类型和范围约定。标题表达最重要的改动；正文在需要时说明原因、行为变化、设计取舍或关联事项。

短提交可以只有标题。不要为了填模板追加无关的测试列表或自我表扬，也不把完成过程写成流水账。提交信息不代替代码差异逐文件复述；读者需要能理解为什么发生这次变化。

拟写信息前确认提交范围，不能写入本次没有包含的工作。表达Skill只负责文案，实际提交或发布按当前任务授权处理。
