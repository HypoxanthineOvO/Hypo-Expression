# 设计

Hypo-Expression 把表达要求分成两层：给人看的要求在 `docs/需求/`，给模型读的规则在 `skills/hypo-exp/`。这份文档说明 Skill 为什么这样组织。用户对文字的要求、不能坏的失败例子写在对应需求文件里，这里不重复。

## 一个入口，三套操作

安装后只有一个 Skill 入口 `hypo-exp`。入口先加载[核心原则](../skills/hypo-exp/references/principles.md)，再按任务读沟通、写作或改稿：

| 任务 | 操作 | 主要区别 |
|---|---|---|
| 与用户交流、讨论原因、汇报工作 | 沟通 | 助手身份，在对话里完成回答 |
| 从材料、事实、提纲或口述观点起草 | 写作 | 作者身份，组织材料和结构 |
| 润色、修改或重写已有文本 | 改稿 | 按授权幅度改，保留信息和格式 |

三种任务的表达原则相同，身份、处理过程和交付方式不同。分成三个入口，模型不必从一段长提示里猜当前该用谁的身份、能改到什么程度；共用规则也只维护一份。写作和改稿可以同时启用沟通要求：正文用作者身份，交付说明用助手身份。

操作文件不规定文体的具体写法。写作和改稿都先读文体大类，再按需读细分文体；沟通有自己的篇幅和交付要求，不套用文章结构。

## 八条原则

核心原则是整个 Skill 的共同判断，其他文件引用它们，不重复写：

1. **正面说明实际内容。** 解释概念说它是什么，提出判断给理由。先否后肯只回应前文确实出现、可能误导读者的观点。
2. **正文只写读者需要的内容。** 事实、判断、条件和读者要做的事留在正文；写作过程、自我约束和核验记录删除。整块都是这类记录时删整块，不换标签保留。
3. **采用恰当的作者身份。** 代写用作者的位置，报道用报道者，README 以项目或开发者为主体，助手汇报用自己的身份。
4. **词句自然，关系明确。** 单个词义和组合习惯都看；正式程度和自然程度分开判断。
5. **保留信息、格式和论证作用。** 改稿默认保留事实、数字、原因、条件、例子、编号、加粗和分节，也保留承担论证作用的过渡句。
6. **先查证，再请作者裁决。** 能查的先查，查过仍要作者取舍的问题带到对话里，不把模型的信息缺口写进正文。
7. **名称稳定，标题有实际含义。** 同一概念用同一名称，标题概括内容或表达作者认可的态度。
8. **按请求交付。** 成稿只呈现内容，内部自查不打印；用户评估效果时给完整原文与改稿对照。

八条原则覆盖所有操作和文体。写作里信息怎么取舍、改稿里哪些内容不能丢，都回到原则 2、5、6，不另写一套。这样规则改动时只需要改一处，三个操作不会各自漂移。

## 语言层：判断三问

多数带 AI 味的写法本身合乎语法，人也照常使用。问题在它们出现在不合适的位置、替代了本该写出的具体内容，或者密集到让读者注意到写法本身。语言层因此不列禁用词表，而是对每类写法说明用错时的样子和改法，并给出三个判断问题：

1. 它在这里承载了什么。删掉后读者是否失去信息、关系或作者的态度。只剩姿态、不剩内容的，改写或删除。
2. 它是否符合当前文体的惯例。校园活动报道结尾一句“为师生理解……提供了参照”是这类稿件的常规收束；同样的句子放在技术介绍每段末尾，就是空话。
3. 同类写法是否过密。一篇文章出现一次排比通常没有问题；段段如此，读者就会看到模板。

禁用词表会把“某词出现在文中”当成问题，无法处理同一个词在不同位置的作用。三问把判断交给语境，也让判例可以解释原因，而不只是列替换词。

## 文体树

文体按作者与读者的关系分为四个大类：

| 大类 | 作者与读者的关系 | 细分文体 |
|---|---|---|
| 报道 | 以事实为主，作者不出场 | 时效消息；活动报道 |
| 论述 | 作者有立场，或以解释为目的 | 观点文章、口述成文、介绍与文案、科普与教程，在大类文件中分节 |
| 说明与汇报 | 帮助读者理解、判断或执行 | 报告（在大类文件中）；仓库文档；界面 |
| 学术 | 遵循领域的研究叙述 | 论文 |

大类文件写该类文本的共同要求，细分文体只补充自己特有的惯例。新的用途先归入最接近的大类；只有它有大类没有覆盖、并且会影响成稿的惯例时，才增加细分文体。这样文体增加时，规则仍是一棵树，不会变成按用途平铺的长列表。

个人栏目的固定格式放在使用者自己的项目规范中，例如某个新闻栏目首句加粗。公开 Skill 只保留可以推广到同类文本的要求，避免把单个栏目的偏好写成通用规则。

## 查证与展示分开

润色和写作都可能需要额外信息。模型在允许访问的资料中查找前后文、定义、事实和已有决定，纠正有依据的错误，补足理解所需背景；查过之后仍有实质冲突或作者取舍，再提出具体问题。

查证与展示分别处理。数据有来源，不等于正文必须写入所有路径、内部标签和核验记录。正文省略这些标签，事实仍要有依据；来源的粒度和位置按文体决定，论文按学术格式引注，面向复核的报告可以保留详细来源，面向沟通和决策的报告突出内容。这样“有依据”和“正文好看”不互相牺牲。

## 判例的位置

判例放在它所说明的规则旁边：搭配和句式的判例在语言层，文体相关的判例在对应文体文件。每条判例写出问题原句、更好的写法和原因，说明具体语境下的处理方向，不作逐词替换表。

这样读规则时能当场看到例子，不必跳到另一个判例库；判例改动也不会和规则分散在两处。只适用于个人栏目或私人项目的判例留在项目规范中，不随公开 Skill 分发。

## 参考项目

规则的主要依据是维护者对实际文本的逐项修改与评价。研究阶段比较了下列写作规范和工具，选择适用于中文表达的原则：

| 资料 | 参考方向 |
|---|---|
| [ASD-STE100](https://www.asd-ste100.org/) | 稳定术语、明确关系、按用途表达；中文规则借鉴这些原则，按中文重新组织 |
| [Google 风格规则](https://github.com/vale-cli/Google) | 自然语气、具体表达、减少空引导语 |
| [Microsoft 风格规则](https://github.com/vale-cli/Microsoft) | 重要信息前置、常用词与稳定术语 |
| [Vale](https://github.com/vale-cli/vale) | 按文体和范围组织可维护的规则 |
| [write-good](https://github.com/btford/write-good) | 识别含混和冗余表达 |
| [proselint](https://github.com/amperser/proselint) | 具体风格问题与适用范围 |
| [AI Writing Humanizer](https://github.com/ZaynJarvis/ai-writing-humanizer) | 中文 AI 写作痕迹的分类：结构、词汇、句法与语气 |
| [Humanizer](https://github.com/blader/humanizer) | 虚构异议、模板化表达及写作过程残留 |
| [Stop That Shit](https://github.com/lennney/stop-that-shit) | 判断限定语对读者的实际作用，处理防御性表述 |
| [avoid-ai-writing](https://github.com/conorbronsdon/avoid-ai-writing) | 保持原意与结构，避免过度改写 |
| [中文文案排版指北](https://github.com/sparanoid/chinese-copywriting-guidelines) | 中文技术文本的标点、数字和专名一致性 |
| [EDA Paper Writing](https://github.com/loujc/eda-paper-writing) | 困难、机制与证据之间的论证关系 |

本项目用中文重新组织操作要求和判例，不随包分发上述标准原文、词典或工具规则库。各参考项目的内容与许可由其原仓库维护。

需求文件按功能分在[表达原则](需求/表达原则.md)、[沟通](需求/沟通.md)、[写作](需求/写作.md)、[改稿](需求/改稿.md)、[文体](需求/文体.md)五份文件中。
