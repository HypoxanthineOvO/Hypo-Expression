# 文体

## 现在

写作和改稿先按作者与读者的关系选大类，读大类文件，再按需读细分文体。四个大类是报道、论述、说明与汇报、学术：报道以事实为主、作者不出场；论述有作者立场或以解释为目的；说明与汇报帮助读者理解、判断或执行；学术遵循领域的研究叙述。大类文件写这类文本的共同要求，细分文体只写自己特有的惯例。用户对当前文本的要求、已有栏目格式和项目规范优先。

## 规则

- 新用途先归入最接近的大类。只有它有大类没有覆盖、并且会影响成稿的惯例时，才增加细分文体。这样文体增加时，规则仍是一棵树，不会变成按用途平铺的长列表。
- 一篇文本跨两类时，按各部分的用途分别处理。新闻评论中的报道部分按报道，评论部分按论述。
- 个人栏目的固定格式，例如某个新闻栏目首句加粗，放在使用者自己的项目规范中。公开 Skill 只保留可以推广到同类文本的要求。
- 仓库文档按用途分 README、版本与提交说明、配套文档，不把一个软件项目的叙述模板推广到数据、演示或研究内容。
- 活动报道的称谓和栏目格式沿用发布方往期报道，单篇参考稿主要用来确定篇幅和结构。
- 科普和教程按读者的理解顺序展开，完整写出机制和步骤，不强加个人态度。教程大纲按大纲交付，润色时不扩写成完整教程。

### 界面文案

- 页面按稳定的使用者视角和总体内容逻辑组织，视觉表达符合内容关系和使用习惯。小字、卡片、图标、对齐和配色是这两条原则在具体场景的应用，不另立大量孤立的禁令。
- 开发条件、Mock 与静态示例说明、真实接入进度、内部标签和数据接入过程，不进入产品界面。页面按目标产品使用者需要组织，不按开发阶段组织。
- 额外解释性注释和小字默认不加。只有用户明确要求展示、并且用途明确时才加入；模型认为“有用”不是添加理由。资料缺口和计算口径单独交给开发者。
- 同类指标一起处理。例如 /opt 与 /home 的存储指标，应当一起放在相应位置或都不放，不能擅自只挑一个突出。
- 先明确内容对象、它们之间的关系和用户要做的操作，再选列表、卡片、表格、时间轴等表达。不能把多个本应独立的单元合并成一张卡，也不能采用“全部删掉”的统一策略。
- 主页面、详情、编辑、返回和反馈共同构成使用过程。页面看起来齐整，不能替代操作是否完整。
- 需求未知时，先用已提供的资料确定任务和展示需要；存在会改变整体设计的重要分歧时集中询问，其余部分直接推进。
- 保留已认可的整体框架、配色和风格。局部修复不自动获得更换色系或整体视觉语言的授权；原视觉不是待解决问题时应当保留。
- 对齐按语义关系确定共同基线、列轨道、间距和容器关系，并在实际页面里查看。元素框顶部相同、页面没有横向溢出，都不足以证明观感已经对齐。
- 文件格式由合适的图标承担识别作用，不靠大块 Markdown 文字标签代替；图标只帮助识别资源，不替代标题、分类和信息组织。
- “干净”不等于视觉寡淡。可以保留动效、玻璃、图像和鲜明色彩，前提是结构清楚、颜色有语义、表现一致。

## 不能坏

- **不把有效信息压成小字或一句空卡。** 财务页删掉了一部分小字，大量不必要的小字仍在，用户判为不合格；算力看板的总览丢掉运行时长，只检查数据对象还在源码里不够，关键信息的可见性、位置和作用都要保留。
- **不擅自重排已认可的结构。** 课程页把同级课程单元 R0–R4 展开、R5–R9 合并，用户判为不合格；试修只是重排并加目录，没有理解页面要呈现的内容。存储路径和源码分组不是产品信息架构。
- **不自行增加界面说明。** 第二轮课程页自行加入 R5–R9 共同主题说明和“按单元顺序浏览”，被用户明确否定；浅色面包屑横条破坏了颜色逻辑。
- **不把开发条件写进产品页面。** “静态示例”“硬件结构已确认”“运行指标为 Mock 示例”不该出现在界面上，也不该换成“已删除”的公告。
- **不把换色当成改善。** 财务页原稿配色更符合用户偏好，换色没有带来改善。
- **不把同类项只处理一半。** 算力看板单独突出 /opt 使用率、不处理 /home，用户指出两者应作为同类一致考虑。
- **不只看运行检查就判定界面合格。** 页面不横向溢出、控件能点，只说明程序跑通；主次、信息位置和视觉关系仍要按真实页面判断。

## 牵连

- 文体文件依赖表达原则和语言层；写作、改稿都按文体选择细则。
- 公开 Skill 里的界面文案细则（`web-ui.md`）只管界面上的文字。上面关于布局、对齐、配色的规则来自前端实验，目前只在候选稿里，尚未并入公开 Skill。并入时同步修改 `web-ui.md`，不把前端实验的临时条件写成通用产品规则。
