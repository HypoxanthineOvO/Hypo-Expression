# 使用说明

安装后的Skill短名是 `hypo-exp`，三个功能都从这一个入口进入。日常直接说“使用 Hypo-Expression 进行……”即可，也可说“用 hypo-exp……”，再说明具体任务。

## 沟通

> 从现在开始，按 Hypo-Expression 的规范跟我交流。讨论原因时把你的理解解释清楚，任务完成后在聊天里交代主要结果。

这项要求在指定会话范围内持续适用。模型应区分讨论、任务执行、进度更新和完成汇报，不把每次聊天都变成正式报告。一次改稿请求不会自动改变以后所有会话的默认行为。

小问题直接在对话中回答。需要交付文件时，回复仍应给出主要结论、理由和必要例子；说明结果的实际影响，不追加防御性声明。日常汇报通常控制在一页以内，复杂情况最多一两页；适合比较或说明关系的内容可以用紧凑图表或交互控件展示。

交付前检查：用户只看本次回复，能否得到答案、理解主要理由，并继续判断或讨论？完整报告按明确要求展开，已有文本的改稿继续默认保留信息和格式。

## 写报告

> 使用 Hypo-Expression，根据项目资料写一份结果报告，面向没有参与实验的同事。需要解释主要结果、比较方法和原因。来源放在文末，篇幅不限制。

结果汇报尽早给主要发现，方法说明讲清输入、步骤和计算关系，决策报告解释建议的依据。报告允许明确判断；事实、推断和建议的关系应当清楚。内部执行记录按报告目的取舍。

## 写新闻

> 使用 Hypo-Expression，将这些来源整理成三条新闻。每条总起首句加粗，后面解释背景和影响，保留来源链接。

模型应区分正式发布、转述、预告、体验和讨论，保持相应的事实归属。原因分析来自评论区时不能改成官方解释。读者需要知道的条件正常交代，不在每条末尾套一段自证。

## 从口述观点写文章

> 使用 Hypo-Expression，把下面口述的观点写成文章。以我的身份写，面向同行，保留明确的态度。请补充必要的事实、例子和解释，信息不足时自行查找相关资料。

模型先理解核心主张、理由、重点和语气，再组织论述。可以整理口头重复与跳跃、补充背景和推理，无需逐项询问。新增论点若改变主旨或价值判断，应与作者讨论。个人经历和动机依据作者材料，不自行编造。

科普和教程根据解释目的展开，不要求每篇文章都使用第一人称或表达强烈态度。

## 改稿

> 使用 Hypo-Expression 润色这篇文章。保留信息、编号和加粗，不缩短篇幅。请给原文与改稿对照。

即使没有重复写“保留信息和格式”，这也是默认要求。允许信息补充与事实查证；如果需要重构全文、缩写或切换文体，在请求中明确即可。

## 论文与项目资料

> 使用 Hypo-Expression 修改这一节，结合项目中的前后章节和相关实验资料。需要我决定的研究解释，请先查资料，再说明问题和依据。

模型应主动定位上下文，保留研究目的、比较条件、因果关系和后续调查的引出。英文论文可要求附中文译文与术语备注。研究本身的限制正常呈现；模型没查清的状态留在讨论中解决。

## 写仓库文档

> 使用 Hypo-Expression 重写这份README。先阅读仓库中的相关资料，介绍它提供什么、为什么整理这些内容、读者如何开始使用，保留有效的用法和链接。

README、Release说明、Changelog和Commit message会按各自用途处理。仓库承载的内容可以不同，模型先理解对象，再选择结构。要写版本或提交说明时，应提供或允许查阅对应版本范围及实际差异；仅撰写文案不等于执行提交或发布。

## 调整偏好

不同使用者可以修改文体细则及判例，保留通用操作入口。例如新闻首句是否加粗、来源放在哪里、外文是否附译文，都可按具体任务覆盖。使用者的明确要求优先于这里的默认偏好。
