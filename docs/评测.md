# 评测

## 方法

评测以作者对实际文本的评价为准。模型可以生成和检查，但不给自己打分，也不做版本排行榜。

一轮实验固定以下条件：

1. 固定 Skill 版本、任务输入和可访问材料范围。
2. 独立执行任务，不向生成模型追加历史批评或其他模型的答案。
3. 保存原始输出，不由主代理先润色。
4. 展示完整原文、输入材料与生成结果；涉及英文语义时附中文翻译和必要备注。
5. 由作者指出具体问题及适用范围，再修改规则。

封闭样本不临时增加外部信息。测试项目查阅能力时，另设可检索的资料范围。写作测试提供事实材料，沟通测试提供请求和必要背景，不用“润色旧回复”代替全部任务。

作者评阅时看这些问题：

- 是否回应了实际任务，作者身份是否合适？
- 是否残留虚构反对观点、自我辩护和生硬搭配？
- 信息、条件、数字和论证作用是否保留？
- 是否擅自缩短篇幅或改变格式？
- 新增事实是否有依据？需要作者决定的问题是否在查阅后提出？
- 报告、新闻与观点文章是否采用了合适的叙述方式？

## 固定样本改稿

样本是八组真实文本：CPU 仿真报告、AI 新闻、模型评测文章、课程要求、教程大纲、新闻说明、README 讨论回复和英文论文小节。每组只提供原文、场景和统一改稿任务；模型不看用户批评、历史改法或其他模型输出。

**第一批（`research/表达语料/实验/corpus-round-01/`）** 改了三组。README 讨论回复（样本 07）用户评价“改得不错”。CPU 报告（样本 01）此前只展示了流程图末尾，内容太少；用户明确反对把“已核验”改成“核验结果”继续保留内部检查，要求整块删掉并改好其他段落。新闻（样本 06）只展示了删除句和来源行，用户认可删掉“已核对摘要页”，完整改稿尚未评价。结论：改标签不能解决内部检查进入正文的问题；展示局部摘句不足以判断改稿。

**第二轮（`research/表达语料/实验/corpus-round-02/`）** 用修订后的 Skill 重改 CPU 报告，允许整块取舍和跨摘录组织；新闻保留上一轮改稿并补全完整对照。用户认为 CPU 和新闻修改后看起来舒服一些，要求继续其余样本。

**第三轮（`research/表达语料/实验/corpus-round-03/`）** 改了新闻、模型评测、课程要求、教程大纲和英文论文五组。

- 新闻（样本 02）：过于精简。要保留加粗的总起首句、原帖给出的高端算力资源和折扣周期等原因，以及评论区的并发上限 1000 和客户调整方式后的资源解释。用“调用量高的客户”，不用“高调用量的客户”。
- 模型评测展示段（样本 03）：改得简洁舒服。这个评价只针对本次展示段，不扩大为完整评测全文通过。
- 课程请假段（样本 04）：不应改成长段，要保留编号步骤和重点加粗。其他注意事项另列：请假超过 20 条会核查并联系老师；请假后的出勤计分需要读者确认。报告者给读者提醒，不写“不能擅自保证”这种模型内部纪律。
- 教程大纲开头（样本 05）：风格大体没问题，但用户不记得原文在做什么，细节还要继续看，不算完整通过。
- 论文（样本 08）：需要中文对照和必要的英文表达备注，并希望查到历史教师认可版本参与比较。后续文件和模型自评不能当作教师认可的证据。

这一轮把“保留原因和条件”“保留编号和加粗”“保留论证句和判断强度”写进了规则。论文的逐句问题是：改稿删掉了 “The latter result directs the investigation beyond copy-group waiting.”，把 suppressing 改成 eliminating、exercise 改成 confirm，判断被加强；“separates their effects” 弱化成 “evaluate each revision”，分别评估两项修改贡献的目的没有保住。

## 三入口复测

`research/表达语料/实验/entry-round-01/` 用一份分层 Skill 跑了六个独立任务：沟通讨论、完成汇报、写作报告、新闻改稿、课程改稿、论文项目查阅。每个任务使用新上下文，只提供该任务材料和固定 Skill；生成代理不看历史回复。论文任务另附十份项目资料副本，测试查阅能力，不覆盖整仓库。

六组完整对照已保存，等待用户评价。模型没有预先排名。

## README 三条件

`research/表达语料/实验/readme-round-01/` 用同一任务、同一事实材料和同一原始 README，让三个新上下文分别生成：

- A：不加载表达或写作 Skill。
- B：加载已发布的 1.0.0。
- C：加载加入通用仓库文档细则的候选 Skill。

三版独立生成，B 和 C 不以 A 的输出为基础，生成代理不看历史批评和彼此输出。原始结果保留，没有主代理润色，也没有质量评分。

这轮**未评完**：`reviews/` 为空，用户还没有对三版给出评价，因此没有选出 README 写法，也没有得出候选细则优于 1.0.0 的结论。

## 前端页面

前端实验使用的 Skill 是候选稿，不是已发布的 1.1.0。评价同样由用户给出。

**第一轮（`research/前端/实验/frontend-round-01/`）** 四个固定原稿：算力看板、课程页、女双签表、财务工作台。用户认为算力看板原框架本来就能看，主要问题是曲线没有轴、总览丢了运行时长，单独突出 /opt 使用率不合理；课程页整体不合格，试修只是重排并加目录，没有理解页面要呈现的内容，R0–R4 展开、R5–R9 合并也不合理；签表的连接关系和卡片观感有改善，但对齐退步；财务页小字清理不足，原配色更符合偏好。开发条件、Mock 示例和“硬件结构已确认”不应进入产品界面。

这一轮先停下改页面，把反馈收拢为两条总原则：稳定的页面使用者视角与总体内容逻辑；符合内容关系及使用习惯的视觉表达。小字、卡片、图标、对齐和配色作为两条原则在具体场景的应用，不新增大量孤立禁令。

**第二轮（`research/前端/实验/frontend-round-02/`）** 从同一批固定原稿重新生成，任务中加入第一轮的用户意图，Skill 加入同类指标一致处理、分类核对、小文字标记转图标和对齐检查。用户表扬算力看板的跳转入口符合直觉；课程页比前轮清楚，但同一教学内容应围绕在线阅读组织，PDF 和原文件下载作为附属操作，自行增加的 R5–R9 共同主题说明和“按单元顺序浏览”被否定，浅色面包屑破坏颜色逻辑；签表内容整体没有明显问题，数字和中英文对齐仍受字体影响；财务页的已扣除说明、待归属金额说明等小字仍不符合要求。用户进一步明确：额外注释和小字默认不加，只有明确要求且用途明确时才加。

**早期页面（`research/前端/实验/early-pages-round-01/`）** 用 candidate-v4 试修 TA-APP、Hypo-LLM 和小说职业百科三个早期页面。构建、类型检查和主要操作路径通过；视觉与信息组织等待用户评阅。这轮只有“原稿与试用 Skill 的改稿”对照，没有同任务的无 Skill 重写，不能把差异全部算作新版规则的独立效果。

**实用页面（`research/前端/实验/practical-round-01/`）** 用 candidate-v3 试修个人财务和乒乓球赛果两个页面。两组使用固定数据、固定字体和可运行快照，截图对照已备好，等待用户评价。

**自主个人主页（`research/前端/实验/homepage-autonomy-round-01/`）** 同一份宏观任务、个人事实和七张图片，分别在不加载 Skill 和加载 candidate-v3 的条件下，从零生成完整静态主页。输入不含旧页面、具体布局或历史批评；桌面、手机和分区截图及可操作页面包已保存，等待用户评价。

## 已知边界

- 已讨论过的样本用于回归测试，不能当作未见样本的泛化结果。前端第一轮之后的重跑属于按用户反馈做的定向回归，改善不能全部归因于 Skill。
- 运行检查、构建通过和页面不横向溢出，只说明程序跑通，不代表设计合格。
- 固定样本保持原样。需要更多上下文时另建输入版本，加入上下文后的表现不能全部算作表达 Skill 的效果。
- 论文的教师认可版本需要可追溯证据。后续文件、模型自评和单篇后期稿都不能替代。
- 实验材料在 `research/` 下，本地保存，暂不进 git。上面的路径用反引号写出，不作为文档链接。

需求文件按功能记录用户要求，见[表达原则](需求/表达原则.md)、[沟通](需求/沟通.md)、[写作](需求/写作.md)、[改稿](需求/改稿.md)和[文体](需求/文体.md)。
